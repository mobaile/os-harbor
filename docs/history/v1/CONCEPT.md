# OS Harbor 构想：从安装到使用，系统始终是一个文件

> **未经端到端验证的设计资料，仅供参考。本文不是实现说明或安装指南。项目目前没有继续开发计划；以下体验、架构与研究顺序均不构成可行性或交付承诺。**

## 1. 想解决的问题

对于已有主系统的电脑，尝试另一套操作系统往往牵涉物理分区、共享启动区和恢复操作。这里希望把系统的生命周期尽可能转变为文件的生命周期：保留原有主系统，在需要时裸机运行另一个系统。

目标体验是：选择安装介质和容量，创建一个系统文件；进入真实硬件上的安装环境，直接把系统装入该文件；以后从管理入口选择它并重启；离线复制文件即可备份，移除文件即可释放对应系统的存储。

目标系统使用真实硬件和自己的内核，不依赖常驻虚拟机。安装和运行使用同一个 RAW 文件，不通过“先安装到物理分区，再转换格式”满足单文件要求。

本文以“主系统”“目标系统”“安装器”和“维护环境”描述角色。具体系统、发行版和工具的行为放在[技术依据与案例审查](FEASIBILITY-EVIDENCE.md)中，不能把某个案例的成功或失败推广为整个架构的结论。

## 2. 核心约束与独立性的定义

1. **保留主系统。** 现有主系统继续安装在原有物理分区上，并保持默认启动地位。
2. **共用镜像仓库。** 每个目标系统对应一个完整 GPT RAW 镜像，内部允许正常分区，不为每套系统分配独立物理分区。
3. **同一文件贯穿安装和使用。** 原版安装器在裸机上写入映射后的镜像，以后从同一文件运行。
4. **项目适配位于镜像外部。** 镜像内不安装项目专用驱动、服务或 hook；允许在外部生成早期启动内容，并准备内存中的关机环境。
5. **运行目标系统自己的内核。** 外部维护环境负责准备和交接，不能以维护内核替代目标内核运行系统。
6. **以一次性请求切换启动。** 管理入口请求下一次启动目标系统，不要求在目标系统无配合的情况下区分重启和关机后开机。

标准 RAW 没有项目专有容器元数据，其他标准工具应能解释其中的磁盘内容。但格式可解释不保证跨硬件迁移、写入物理盘后启动或接入其他运行环境一定成功。

镜像独立性要求完整系统状态位于文件内，外部索引和启动缓存可以重建。它仍依赖仓库、存储映射和引导环境；“镜像内没有项目专用代码”也不等于目标系统无需任何外部适配。

## 3. 方案演变中的取舍

| 阶段 | 关注点 | 留下的问题 |
|---|---|---|
| 传统多系统 | 通过独立分区和引导菜单管理系统 | 每套系统的空间分配、移除与恢复成本高。 |
| 镜像文件管理 | 将完整系统保存为文件，借助外部入口启动 | 文件格式与启动工具可能要求系统内部配合。 |
| 镜像独立 | 将项目适配移到外部 | 目标内核接管后仍须重建根设备依赖。 |
| 公共仓库 | 多套系统共用存储空间 | 主系统访问、启动时挂载、并发写入和容量管理更复杂。 |
| 完整生命周期 | 让安装、运行、备份和移除围绕同一文件进行 | 必须同时解决安装兼容、运行可靠性与异常恢复。 |

完整磁盘镜像可以把分区结构、启动资料、系统和用户数据放在同一容器中。相比把根文件系统、内核和配置作为多份独立状态管理，它更符合离线复制整个系统的目标；代价是外部环境必须解析镜像内部布局。

仓库文件系统的选择需要权衡主系统访问、早期挂载能力、空间分配、快照和复制成本。主体架构不绑定具体实现，已有候选技术也不代表兼容性和可靠性已被证明。

现有代码停留在较早的管理实验阶段，不能直接作为当前架构的入口。历史实现见[代码说明](../../../deprecated/docs/EXPERIMENTAL-CODE.md)。

## 4. 候选架构与职责

```text
主系统管理入口
    │ 选择镜像／提交任务／请求一次性启动
    ▼
独立引导与维护环境
    ├── 安装
    │   └── 准备存储与权限边界 → 映射镜像 → 运行安装器
    │
    └── 启动
        └── 读取镜像启动资料 → 准备外置适配 → 交接目标内核
                                                    │
                                      重建映射 → 进入目标系统
                                                    │ 关机
                                      外部清理环境 → 释放存储
```

图中各部分均为候选设计，当前项目没有实现完整链路。

### 仓库与管理入口

仓库存放完整系统镜像，管理入口保存选择和任务请求。镜像应通过仓库的稳定标识及相对路径定位，不能依赖会变化的盘符或设备编号。

主系统不必直接写入仓库文件系统；也可以把操作排入独立维护环境，在下一次启动执行。这样会增加重启和等待成本，但能减少主系统侧必须实现的存储能力。任务状态、日志和可重建索引需要明确的交换方式。

一次性启动请求和默认启动顺序是不同职责。还需要验证请求失败、目标不可用或外部介质缺失时，主系统能够按预期恢复启动。

### 安装环境

安装环境将 RAW 呈现为安装器接受的块设备，并保护非目标物理磁盘和固件状态。设备能被映射，仅说明有了候选目标；兼容验证还要覆盖设备筛选、分区、格式化、引导安装、完成检查和退出行为。

映射属于建立它的运行环境。若安装过程更换内核，不能假定已有映射自然保留；必须明确由哪个环境建立、持有和释放映射，以及安装器在哪个环境中执行。

设备列表隐藏不等于写入隔离。仓库所在物理盘需要正常工作，同时安装器不应获得对非目标存储和固件状态的任意写入能力。保护这些资源与满足原版安装器的权限要求，必须一起验证。

安装阶段可以采用与运行阶段不同的映射机制，前提是两者读写同一 RAW 的相同磁盘内容，不引入格式转换或第二份系统状态。

### 启动与内核交接

外部环境负责读取镜像内的启动资料、准备适配内容，并加载目标系统自己的内核。目标内核接管后，需要识别真实存储、访问仓库、重建镜像映射，再进入真正的根文件系统。

这条链路需要匹配目标内核的驱动与模块、正确的启动参数，以及可执行的早期准备入口。能够读取镜像或组合启动文件，不代表这些步骤会自动完成。

外部引导器直接加载目标内核，或者由维护环境交接到目标内核，都是候选方向。应根据可验证的接口和硬件行为选择，不把某一种交接机制视为所有系统的通用答案。

### 运行与关机

目标系统运行期间，内层文件系统依赖映射，映射又依赖外层仓库。外层存储必须持续可用，不能被运行环境误卸载或提前释放。

正常关机需要先停止依赖存储的使用者，再按依赖顺序卸载内层文件系统、释放中间映射，最后同步并卸载外层仓库。外部早期启动环境可以研究在内存中准备清理环境，使清理过程不依赖已经卸载的目标根文件系统。

现有接口为这种设计提供了依据，但每种启动与关机框架仍需适配验证。正常启动、正常关机和连续冷启动后的数据一致性，应共同构成运行链路的验收条件。

### 更新、备份与恢复

目标系统可以正常写入镜像。系统更新生成的内核、模块和启动资料仍以镜像内的内容为准，外部副本只作为可重建缓存。

不在镜像内安装更新 hook 的候选办法，是外部环境在启动前重新识别实际启动资料，检查一致性并重建必要缓存。缓存回退不能撤销镜像内部更新，系统恢复仍需有效备份或另行验证的恢复机制。

备份与克隆首先考虑离线复制完整 RAW。克隆会复制内部标识，设备发现应限定在本次选中的镜像内。并发写入、外层空间耗尽、复制中断、断电和恢复失败都必须有明确处理方式。

## 5. 宏观可行性分析

**核心方向有技术依据，但完整方案的可行性取决于安装、启动、运行和恢复能否共同满足约束。** 已查证的机制只覆盖部分内核、存储接口与启动框架，宏观表述不扩大实际支持范围。

| 维度 | 判断 | 仍需解决的问题 |
|---|---|---|
| 文件承载完整系统 | 标准磁盘格式与文件映射机制提供基础。 | 容量分配、内部布局识别、存储错误与性能。 |
| 裸机运行 | 外部准备后交接目标内核有技术依据。 | 目标内核功能、驱动匹配、根设备发现与硬件状态。 |
| 镜像内无项目代码 | 可研究由外部启动和关机环境承担适配。 | 挂载保留、关机接口以及更新后的兼容性。 |
| 原版安装 | 可以提供候选块设备与安装入口。 | 设备接受程度、固件写入、权限边界和完整安装流程。 |
| 主系统保留 | 可设计独立维护入口与一次性启动请求。 | 安装、失败和恢复过程中的实际保护效果。 |
| 多系统产品化 | 架构可以承载多个镜像。 | 兼容矩阵、版本变化、可恢复性和持续维护成本。 |

最重要的工程边界是：**存储格式可以统一，安装器和启动框架的行为不会因此自动统一。** 某种映射在一个案例中被拒绝，说明该组合需要调整；某个案例成功，也只能证明对应版本和条件。

运行时直接使用真实硬件，不等于整体性能与物理分区相同。额外的存储层次仍可能影响延迟、随机读写和持续写入。预分配镜像空间可以缩小首轮实验变量，但不能代替容量管理与故障恢复。

当前适合验证限定范围的原型，尚不具备承诺通用兼容或稳定产品交付的依据。具体机制、案例源码与证据限制见[技术依据与案例审查](FEASIBILITY-EVIDENCE.md)。

## 6. 如何验证

以下是研究方法，不是开发计划或操作指令。首轮应固定一个目标版本、一个内部布局、一组测试硬件和一种仓库存储配置，减少并行变化的因素。

安装和运行可分别验证：

| 验证线 | 必须取得的证据 |
|---|---|
| 运行 | 使用镜像自己的内核到达可写系统；镜像内无项目专用代码；硬件正常；关机和冷启动后数据完整；更新内核后可启动，外部缓存丢失后可重建。 |
| 安装 | 固定安装介质和依赖版本；明确映射及权限边界；证明非目标写入被阻止、固件状态得到正确处理；原版安装器完整结束安装。 |

运行验证可以使用准备好的镜像，部分问题可以在虚拟环境中排查；这些都不能证明裸机安装要求，也不能代替实机硬件验证。两条线通过后，还须连接为完整流程：

> 原版安装器在裸机上写入 RAW → 从同一 RAW 运行 → 正常关机与冷启动 → 系统更新后再次启动。

随后验证离线备份恢复、克隆标识冲突、空间不足、复制中断、断电恢复和存储性能，最后接入主系统管理入口，验证默认启动及失败返回。

若实现需要修改原版安装器，或向镜像内安装项目专用代码，应记录哪一项核心约束未达到。不得用部分步骤成功替代完整流程，也不得用格式检查或旧代码测试覆盖待验证状态。
