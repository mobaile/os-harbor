# OS Harbor 方案 v2：用一个物理分区承载完整系统磁盘

> **设计构想 · 2026-09-11。未经端到端验证，不是安装教程或可用产品。本文记录期望达到的行为、已有技术基础和未解决的问题，不承诺透明隔离或通用启动能力。**

## 1. 目标与使用体验

在保留 Windows 默认启动方式的前提下，为每套 Linux 分配一个专用物理分区。管理入口选择系统并请求下一次启动；重启后 Windows 不运行，所选 Linux 使用自己的内核和真实硬件。

承载分区保存的是一整块系统磁盘的内容，而不仅是一个 Linux 根文件系统。安装器可以在提供给它的磁盘视图内创建 GPT、EFI 分区、根分区以及其他内部布局，安装与后续运行始终读写同一承载分区。

期望效果是：**Linux 无需知道外部布局，只认为自己安装在一块完整硬盘上。** 它不能访问承载分区以外的空间，也不需要通过项目专用程序适应受限权限。这个要求包含设备呈现和访问边界两部分，当前均没有完整实现证据。

本文记录第二版构想。第一版原文与当时的研究记录保存在[历史构想](history/v1/README.md)。

## 2. 核心约束

1. **保留 Windows。** 现有分区及引导文件得到保护，Windows 保持默认启动项；日常切换只使用一次性启动请求。
2. **一个承载分区对应一套完整系统。** 系统内容直接位于物理分区的块空间，不依赖外层文件系统中的 RAW 文件。
3. **安装与运行使用同一份内容。** 原版安装器在裸机上写入所提供的磁盘视图，之后从同一承载分区运行。
4. **目标内核裸机运行。** 使用目标系统自己的内核，不修改其源码，不使用虚拟机、常驻虚拟化宿主或容器替代目标运行环境。
5. **项目适配外置。** 不向内部系统持久安装项目专用驱动、服务或 hook；可以研究在外部准备启动适配副本、索引和可重建缓存。
6. **目标系统无感。** 对安装器、系统及管理工具提供正常完整磁盘的行为，同时维持外部存储的不可访问性；不能通过只限制普通用户权限来宣称满足此项。

不修改内核源码，不等于无需启动配置或标准模块。若某条路径需要特定内核功能、匹配模块或外部 initramfs 适配，应明确记录条件。若它只能通过改变上述约束运行，必须登记为未满足原目标。

## 3. 存储结构与两版差异

```text
第一版：物理硬盘 → 外层文件系统 → system.raw → 内部 GPT → 系统与数据
第二版：物理硬盘 → 专用承载分区 ───────────→ 内部 GPT → 系统与数据
```

假设承载分区为 200GB，目标磁盘视图的容量就以这段空间为边界，逻辑起点对应承载分区起点。内部主、备分区表和所有内部文件系统都必须位于这段范围内，不能将目标视图的地址误解释为物理整盘地址。

外层分区表用于定位承载空间，内层分区表由目标安装器管理。解析内层布局需要明确容量、偏移与扇区单位；主板固件不能被假定会自动识别嵌套的 EFI 分区。

承载分区应通过稳定的磁盘与分区标识定位，并重新核对实际边界。盘符、设备编号或旧的偏移缓存不足以成为写入依据。克隆会复制内部标识，内部根设备发现必须限定在本次选择的承载空间内。

| 项目 | 第一版：文件承载 | 第二版：分区承载 |
|---|---|---|
| 完整系统状态 | 一个 RAW 文件 | 一个专用物理分区的块内容 |
| 外层存储依赖 | 先访问外层文件系统，再访问文件 | 直接访问承载分区，无系统文件后端 |
| 映射与清理 | 文件映射及外层文件系统依赖 | 分区或块设备映射，仍需维护内部依赖 |
| 容量 | 管理文件容量与外层可用空间 | 分配真实分区，扩缩容涉及外层和内层布局 |
| 备份与恢复 | 离线复制完整文件 | 离线复制或导出整个承载分区的块内容 |
| 移除 | 移除文件及外部登记 | 解除登记并回收承载分区，属于磁盘管理操作 |
| 透明隔离 | 未解决 | 不会因替换后端自动解决 |

第二版省去了文件碎片、系统文件与外层空间分配之间的关系，以及为读取系统文件而挂载外层文件系统的步骤。它没有消除内部文件系统碎片、内部空间耗尽、断电一致性或设备错误，也不能仅凭层次减少就宣称性能等同普通物理分区安装。

外部索引、日志和启动缓存仍可使用普通文件；“不使用文件承载系统”不是禁止任何辅助文件。备份也可导出为镜像文件，但正常安装与运行仍读写物理承载分区。

## 4. 候选安装与启动路径

```text
Windows 管理入口
    │ 选择系统／提交安装维护任务／提交一次性启动请求
    ▼
外部启动或维护环境
    ├── 定位承载分区，核对边界
    ├── 安装：建立磁盘视图与保护边界 → 运行原版安装器
    └── 启动：读取内部启动资料 → 准备外部适配 → 加载目标内核
                                                        │
                         在目标内核环境中建立所需映射与根设备
                                                        │
                                       运行 → 清理存储 → 关机或重启
```

这些步骤是待验证的职责划分，不是现有程序流程。

### 块设备呈现

`dm-linear` 为区域映射提供基础；LIO BLOCK 与本地 loopback 可作为将块存储呈现为本机 SCSI 设备的另一项研究候选。后端选择尚未确定。标准模块是否可用、内层分区如何发现、安装器是否接受设备类型与名称，都需要实际验证。

映射设备的普通读写范围与物理盘的访问权限不是同一件事。建立映射不会让原始磁盘消失，也不证明整盘访问、控制器命令或其他路径已被阻止。当前没有满足全部约束的透明隔离方案；不能用“更像普通硬盘的设备名”代替这一缺失。

### 原版安装与固件保护

原版安装器需要完成设备发现、内部布局创建、引导安装和完成检查。映射可读写仅是前置条件。安装阶段必须另行验证 Windows 分区、外层分区表、原有 EFI 文件与固件启动状态受到保护。

只在界面隐藏真实盘不足以构成保护；仅阻止 EFI 变量写入也可能使安装器失败。安装器希望写入的内部引导资料与真实主板的启动变量需分别处理，其兼容方式尚未确定。

### 目标内核与启动适配

由外部环境解析内层启动资料、准备适配副本，再加载目标系统自己的内核，是候选方向。设备映射属于建立它的内核运行环境，换内核后不能假定映射自动保留；目标内核仍需在早期启动中建立必要的映射并找到根设备。

外部早期启动适配不能被当作已经解决“内核只发现指定磁盘”的机制。它可能依赖标准存储驱动和模块，但裸机内核对原始硬件的枚举仍是透明隔离必须解决的问题。

### Windows 默认项与一次性启动

保留 Windows 默认启动顺序，使用 UEFI `BootNext` 请求一次启动目标入口，是管理入口的目标行为。它要求存在固件能够实际启动的入口；嵌套的 EFI 分区不能直接被视为这样的入口。

不替换 Windows 引导文件仍可能需要一个独立启动入口及外部适配资源。入口的位置、内部引导资料的接入和固件注册方式尚未确定。一次性请求不会自动保护安装阶段的永久启动顺序，也不能保证目标系统卡死后自动返回 Windows。

## 5. 生命周期

- **运行与关机：** 内部文件系统、加密层和分区映射按依赖顺序卸载、同步和释放。外层文件系统虽已省去，存储清理依然需要验证。
- **系统更新：** 内部系统产生的内核、模块和引导资料为准；外部副本仅作可重建缓存。无内部项目 hook 条件下如何发现更新、准备匹配适配并恢复启动，尚未验证。
- **备份与恢复：** 对离线承载分区保存完整块内容以及重建外部定位所需的信息。恢复前核对目标容量与身份，不假定复制到不同大小空间后内部 GPT 自动有效。
- **容量与移除：** 预留专用空间，扩缩容同时考虑外部边界和内部文件系统。回收承载分区属于有影响的磁盘操作，不提供“删除文件即可移除”的承诺。
- **异常恢复：** 承载分区缺失、边界变化、标识重复或缓存不一致时应停止相关写入并报告。断电、恢复中断和启动失败后的实际恢复策略需要证据。

第一轮研究固定单一系统版本与布局。加密、休眠、swap、多磁盘组合和不同启动框架均为需要单独验证的条件，不推定通用支持。

## 6. 可行性判断与验证顺序

**分区后端简化有技术依据；完整系统的透明隔离尚未成立。** 如果无法在不使用虚拟机、容器和修改目标内核源码的条件下实现唯一磁盘视图，就不能将普通映射启动登记为第二版完成。

后续研究应先分别验证存储映射和透明隔离，再评估原版安装及目标内核启动，最后连接更新、关机、备份恢复和 Windows 管理入口。任何单项成功都不能覆盖其他未满足的约束。

具体验收场景及实际检查范围见[验证记录](VALIDATION.md)，机制来源和证据边界见[技术依据](FEASIBILITY-EVIDENCE.md)。目前没有第二版运行代码、安装步骤或实机成功记录。
