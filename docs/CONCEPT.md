# OS Harbor 构想：从安装到使用，Linux 始终是一个文件

> **未经验证的设计资料，仅供参考。本文不是实现说明或安装指南。项目目前没有继续开发计划；以下体验、架构与研究顺序均不构成可行性或交付承诺。**

## 1. 想解决的问题

对于已有 Windows 的电脑，尝试另一套操作系统往往牵涉物理分区、共享启动区和恢复操作。这里希望把“系统的生命周期”尽可能转变为“文件的生命周期”，保留原 Windows，在需要时裸机运行另一个系统。

目标体验是：选择 ISO 和容量，创建一个系统文件；重启进入真实硬件上的安装器，直接把系统装入该文件；以后从 Windows 选择它并重启；离线复制这个文件即可保存完整系统状态，移除它即可释放对应系统的存储。

这不是在 Windows 桌面内同时运行 Linux。运行中的目标系统应使用真实硬件以及自己的内核，不依赖常驻虚拟机。安装目标也是同一个 RAW 文件，不通过“先安装到物理分区，再转换格式”达成单文件效果。

## 2. 核心约束与独立性的定义

1. 现有 Windows 例外：它继续安装在原来的物理分区上。
2. Linux 共用一个仓库分区，初步考虑 ext4；每个系统是完整 GPT RAW 镜像，内部允许正常分区。
3. 原版安装器在裸机上直接写入映射后的镜像；裸机安装是构想的一部分，不能以虚拟机安装代替此项证明。
4. 镜像内不安装项目专用驱动、服务、daemon 或 hook。允许在镜像外生成早期启动适配内容。
5. 使用目标系统自己的内核及匹配模块，避免用通用维护内核直接替代目标内核运行桌面。
6. Windows 入口只请求一次性启动；不强求无系统配合地区分“Linux 重启”和“关机后开机”。

标准 RAW 没有项目专有容器元数据。理想情况下，其他标准工具仍可将它作为磁盘检查、挂载或接入虚拟机。但格式标准只说明可解释性，不保证更换机器或写入物理盘后一定能启动。

镜像独立不等于“完全没有外部依赖”：文件中的系统需要外层文件系统、存储映射和引导环境。要求是完整系统状态在文件中，项目索引和启动缓存可以从镜像重新生成。删除管理程序不应让镜像变成无法被其他工具理解的私有数据。

## 3. 思路如何演变

| 阶段 | 思路 | 遗留问题 |
|---|---|---|
| 传统多系统 | 多个物理分区与引导菜单 | 每套系统的存储和引导管理复杂。 |
| 借鉴 Ventoy | NTFS 上存放完整系统镜像，用 USB 入口启动 | Ventoy 有自己的 Linux 镜像准备要求；本项目未验证 Omarchy 链路。 |
| 追求镜像独立 | 不在 Linux 内安装 vtoyboot 或项目专用代码 | 单靠 EFI 阶段读到文件，不足以解决 Linux 接管后的根设备发现。 |
| Linux 仓库分区 | 使用 ext4 存放多个 RAW，借助 loop 等标准能力 | Windows 管理更复杂；仍需要早期用户空间建立映射。 |
| 单文件完整生命周期 | 安装器直接写入 RAW，以后从同一个 RAW 裸机启动 | 安装器兼容、写入隔离和外置启动适配尚未验证。 |

中途曾考虑“root.img + 独立内核 + manifest”的目录结构。最终构想更倾向完整 GPT RAW：内核和引导资料仍以镜像中的内容为准，外部副本仅作为可重建缓存，不成为另一份必须同步备份的系统状态。

ext4 是为了缩小早期映射问题的范围，不表示已经验证可靠。Btrfs 仓库可能有利于快照和 reflink 克隆，但会增加复杂性；NTFS 更方便 Windows 管理，却带来另一组早期挂载和加密约束。未对这些选择做性能或可靠性比较。

现有代码停留在较早的 Ventoy 路线，没有实现最后两阶段。保留它是为了展示探索过程，不能把旧 CLI 当作新架构入口。

## 4. 候选架构与数据流

```text
Windows 管理入口（未实现）
    │ 选择系统／提交任务／请求下一次启动
    ▼
独立 EFI 与 Linux 维护环境（未实现）
    │
    ├── 安装：挂载仓库 → 创建 RAW → NBD 映射 → 原版安装器
    │
    └── 启动：读取 RAW 中的内核和启动资料 → 生成外置适配
                                              │
                                              ▼
                                目标系统自己的内核接管硬件
                                              │
                               重新挂载仓库 → loop → 根分区
                                              │
                                              ▼
                                        目标 Linux
```

### 仓库和管理入口

候选布局为 ext4 仓库中的 `/systems/<系统名>.raw`。初步研究可使用独立测试磁盘与独立 USB 引导环境，避免一开始就处理 Windows 分区缩容。安装维护任务、结果和可重建索引可放在双方能访问的交换区；镜像路径应以仓库 UUID 和相对路径识别，不能依赖固定盘符或设备编号。

Windows 不必直接写 ext4：可把工作排入 Linux 维护环境，在下一次启动执行。这牺牲即时管理体验，但能避免自制 Windows 文件系统写入驱动。WSL 也不是所有布局的通用答案：其物理盘挂载需要附加整个磁盘，不能直接挂载仍被 Windows 占用的启动盘上的分区。[微软 WSL 文档](https://learn.microsoft.com/en-us/windows/wsl/wsl2-mount-disk)

### 安装路径

QEMU NBD 可在 Linux 中把磁盘镜像绑定为 `/dev/nbdX`。这提供候选安装目标，但安装器的设备筛选、分区命名、引导安装和自动重启行为仍需逐项验证。[QEMU NBD 官方文档](https://www.qemu.org/docs/master/tools/qemu-nbd.html)

安装环境需要保护实际物理盘和固件变量。把危险磁盘从界面隐藏并不构成写入隔离；仓库所在盘还必须由维护层正常访问，因此不能简单假设“把所有真实盘设为只读”就解决问题。设备权限、命名空间和安装器权限边界都是待研究内容。

Omarchy 安装器与 ISO 的行为应以固定版本的上游源码和实际运行结果为准；不能仅因为它基于 Arch 就认为支持 NBD。[Omarchy ISO 与安装器源码](https://github.com/omacom/omarchy-iso)

### 启动路径

外部环境读到镜像以后，目标内核仍需要自己识别物理存储、挂载仓库、建立文件到块设备的映射，再发现真正的根分区。早期用户空间正是处理根文件系统准备的环节。[Linux initrd 文档](https://docs.kernel.org/admin-guide/initrd.html)

候选办法是从镜像提取目标内核和 initramfs，在外部构建适配副本；维护 Linux 可研究通过 kexec 交接到目标内核。kexec 只是候选方向，硬件重新初始化、固件状态和驱动兼容仍需实测，不是已选定并验证的实现。也可以研究由外部引导器直接加载目标内核，二者都没有在本项目中实现。

Linux 的 initramfs 格式支持组合归档，但这不意味着附加脚本会自动运行。实现仍需明确入口和执行顺序，并针对目标 initramfs 框架适配，加载与目标内核版本匹配的存储、ext4、loop 和根文件系统模块。[Linux initramfs 格式文档](https://docs.kernel.org/driver-api/early-userspace/buffer-format.html)

进入目标系统后，外层仓库不能被错误卸载；正常关机时也必须先处理内层文件系统，再同步并释放外层存储。加密根分区、Btrfs 子卷、swap、休眠和 Secure Boot 都会增加条件。这里没有解决这些条件，也不宣称一套外部片段能启动任意 Linux。

### 生命周期

备份和克隆应在离线状态复制完整 RAW。系统可写运行是预期行为，不应仅因文件修改时间改变就认为镜像失效。涉及内核更新时，需要重新识别启动资料并更新外部缓存；缓存回退不能撤销镜像内部更新。

克隆会复制内部 UUID，不能全局按 UUID 随意寻找根设备；应限定在本次选中镜像的映射设备内。并发写入、空间不足、复制中断和断电恢复也必须纳入未来实现。上述管理行为目前均未实现。

## 5. 已有组件不等于已有完整方案

| 问题 | 能确认的基础 | 本项目尚未证明的部分 |
|---|---|---|
| 文件作为磁盘 | Linux loop 与 QEMU NBD 提供映射能力 | 原版安装器完整接受并正确安装到目标。 |
| 根文件系统准备 | initramfs 可进行早期存储准备 | 外置适配、根切换和关机链路可靠。 |
| 独立镜像 | RAW 可表达完整磁盘内容 | 删除缓存后可重建启动，换工具后仍可用。 |
| 裸机运行 | Linux 本身运行在物理硬件上 | 维护环境交接后的 GPU、网络、存储正常。 |
| 系统更新 | 镜像内容可以变化 | 更新内核、模块、引导器之后仍能启动。 |
| Windows 保留 | 可以设计独立引导入口 | 安装和恢复过程确实未损坏原 Windows。 |

## 6. 后来者可以怎样验证

以下仅为研究顺序，不是本项目的开发计划或操作指令：

1. 固定一个 Omarchy ISO 版本，证明原版安装器接受 RAW 的 NBD 映射；先验证非目标磁盘写入会被阻止，再做裸机实验。
2. 使用同一个 RAW 和其中自己的内核，验证外置适配可以到达可写桌面，且不向镜像内安装项目代码。
3. 验证写入持久化、正常关机、再次启动、GPU、网络和输入设备，不能只以启动日志出现为成功。
4. 验证内核更新、缓存丢失重建、离线备份恢复、重复 UUID、空间不足和中断恢复。
5. 最后研究 Windows 一次性启动入口，并验证原 Windows 默认启动和拔除引导介质后的行为。

若安装器或目标启动框架要求修改，应清楚记录妥协，不将其包装成“原版零改动”。若关键验证失败，这个构想仍然是未证实的假设。

## 7. 参考资料与项目边界

- [Ventoy Linux vDisk / vtoyboot](https://www.ventoy.net/en/plugin_vtoyboot.html)：早期实验路线及其准备要求；不是本项目新构想的验证证据。
- [QEMU NBD](https://www.qemu.org/docs/master/tools/qemu-nbd.html)：镜像导出和块设备连接。
- [Linux loop 设备说明](https://docs.kernel.org/admin-guide/devices.html)：标准文件到块设备机制的背景。
- [Linux initrd](https://docs.kernel.org/admin-guide/initrd.html) 与 [initramfs 格式](https://docs.kernel.org/driver-api/early-userspace/buffer-format.html)：早期用户空间及归档机制。
- [Omarchy 安装器源码](https://github.com/omacom/omarchy-iso)：版本相关行为的核对入口。
- [WSL 物理磁盘挂载](https://learn.microsoft.com/en-us/windows/wsl/wsl2-mount-disk)：Windows 访问 Linux 仓库的约束。

这些是独立上游项目的资料，内容可能随版本变化。OS Harbor 与这些项目没有隶属或背书关系，也不宣称发明了文件作为块设备的技术。这里希望提供的参考价值是围绕“同一个标准文件贯穿安装和裸机使用”组织体验，并诚实列出尚未跨越的工程边界。
