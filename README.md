# OS Harbor · 方案 v2：一个分区承载一套系统

> **这是一个尚未实现的多系统管理构想。这里记录完整的理想目标，具体实现留给后续探索；方案版本不代表软件发行版本。**

**Unverified concept, not a working installer or boot manager.** Concept v2 uses a dedicated physical partition to hold an entire system disk. Transparent isolation and end-to-end bootability have not been demonstrated.

## 想实现的体验

平时电脑默认进入 Windows。需要另一套系统时，在 Windows 管理入口选择它并重启，Windows 停止运行，由所选 Linux 使用自己的内核在真实硬件上运行。

**外面是一个专用物理分区，里面是一套完整的系统磁盘。** 安装器和 Linux 理想中只看到一块属于自己的完整硬盘，能够正常分区、格式化、安装引导和读写数据，无需知道这块“硬盘”实际来自另一块硬盘上的一个分区。

## 理想目标：每套系统都拥有一块只属于自己的硬盘

**在外部，一个物理分区代表一套系统；在系统内部，它就是整块硬盘。** Linux 不需要知道自己被映射或被隔离，也不需要配合任何特殊约定。

- **始终只见自己的硬盘。** 从原版安装器启动到日常运行、系统更新和重启，设备容量、地址与可见范围保持一致，其他硬盘和外部系统分区不出现在它的世界里。
- **自己的硬盘完全自主。** 系统可以正常分区、格式化、安装引导、更新内核和管理磁盘；即使执行“清空整盘”，影响范围也始终只有自己的承载分区。
- **完整的裸机体验。** 使用原版系统、自己的内核和真实硬件，无需虚拟机、容器或内部项目组件，也无需牺牲正常系统管理能力换取隔离。
- **Windows 始终是默认入口。** 主动选择时才重启进入另一套系统，下一次正常启动回到 Windows；目标系统的安装与引导设置不改变 Windows 的分区、引导文件和默认地位。

理想中，这种磁盘视图在操作系统之外准备好，并在它运行期间始终成立。固件、存储硬件或未来机制如何协作，留给实现者决定；我们不预先用今天已有的接口、产品或相近方案限定答案。

完整目标与使用过程见[理想目标与使用体验](docs/IDEAL-IMPLEMENTATION.md)。我们将它公开保留下来，供有相同需求的人、有实现能力的人，以及帮助他们研究问题的 AI 工具阅读和继续探索。

## 核心结构

```text
物理硬盘
├── Windows 分区与原有引导
├── 系统 A 的承载分区
│   └── 完整磁盘内容：内部 GPT → EFI 分区、Linux 根分区、数据
└── 系统 B 的承载分区
    └── 完整磁盘内容：内部 GPT → EFI 分区、Linux 根分区、数据

理想中的系统入口（尚未实现）
└── 选择承载分区 → 提供唯一完整硬盘视图 → 原版系统正常安装与运行
```

- 每套系统使用一个专用物理分区，直接读写其块空间，不再通过外层文件系统中的系统文件存储。
- 同一承载分区贯穿安装和运行，内部保留自己的分区表、引导文件、系统和数据。
- 目标系统使用自己的内核，不修改目标内核源码，不采用虚拟机或容器路线；项目适配放在系统外部。
- Windows 保持默认启动地位，管理入口仅提交一次性启动请求；启动衔接由系统外部完成。
- 备份、恢复和容量管理围绕承载分区进行，不能再把删除或复制一个文件直接等同于移除或备份系统。

## 构想与实现的关系

当前没有实现或实机验证结果。我们先明确希望获得的完整功能，再由后续研究寻找实现方法。已有机制的资料审查仅供参考，不是指定路线，也不是降低目标的理由。

局部原型可以积累证据，但只有正常使用、透明隔离、主系统保护和完整生命周期共同成立，才算达到了这里描述的理想。
